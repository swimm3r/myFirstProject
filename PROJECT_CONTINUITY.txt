10. ROOT CAUSE FOUND: WEBTORRENT DEFAULT FULL-TORRENT SELECTION (2026-11-26)
Verified against the deployed project dependency range (server/package.json: webtorrent ^1.9.7) and upstream WebTorrent v1.9.7 source:
- In lib/torrent.js, metadata initialization (around lines 504-517) creates a default low-priority selection covering every piece: select(0, pieces.length - 1, false), unless BEP53 file selection is supplied.
- The worker previously called torrent.files.forEach(file => file.deselect()). In WebTorrent v1.9.7, File.deselect() calls torrent.deselect(file._startPiece, file._endPiece, false), which only removes an exact file interval. It cannot remove the one full-torrent interval. Therefore the default full-torrent selection remained active.
- WebTorrent's selection scheduler downloads pieces belonging to every active selection. The worker's priority-2 rolling window did not constrain or replace the still-active priority-0 full-torrent selection. The custom RingMemoryStore.put() retained every verified piece, so storeBytes grew with torrent-wide downloading (observed ~390-444 MB in ~10 seconds) despite a nominal 64 MiB window. This is the confirmed primary cause of the RAM growth.
- Secondary avoidable overhead: WebTorrent wraps custom stores in CacheChunkStore by default with 20 cache slots unless storeCacheSlots is set to 0. RingMemoryStore is already RAM-backed but is not instanceof MemoryChunkStore, so the default wrapper can retain another 20 pieces in memory. This is bounded overhead, not the hundreds-of-MB root cause.

Fix branch: fix/remove-webtorrent-default-full-selection
- Created directly from latest main commit 75bf0c024bb96faac02865fac7be10bf0325eab1 (verified main and new branch identical before edits; main was 3 commits ahead of PR #6 base).
- server/downloader/worker.js changes:
  1) Explicitly deselect the exact global default interval (0..pieces.length-1, priority false) after torrent ready; do not rely on per-file deselect calls.
  2) Log TORRENT_DEFAULT_SELECTION_REMOVED and expose current WebTorrent selection intervals/priorities in /status diagnostics, so runtime logs can prove only the stream and rolling-window selections remain.
  3) Set storeCacheSlots: 0 to avoid the redundant CacheChunkStore layer on top of the custom RAM store.
  4) Keep the current 64 MiB rolling window, 8 MiB rewind cushion, 8 MiB prebuffer, and 650 MB watchdog unchanged. No speculative buffer/limit tuning.
- Upstream source reviewed: WebTorrent v1.9.7 lib/torrent.js (default selection, select/deselect exact-match behavior, CacheChunkStore wrapping) and lib/file.js (File.deselect interval), lib/file-stream.js (priority-1 stream selection).
- Runtime validation on Raspberry Pi/Kodi is still required. Expected result: storeBytes should stay near the selected rolling window plus rewind/active stream/in-flight pieces, not grow by hundreds of MB. Check TORRENT_DEFAULT_SELECTION_REMOVED and torrentSelections in worker metrics.

11. REPLACEMENT IMPLEMENTATION FOR THE FAILED PR #9 APPROACH (2026-11-26)
Base:
- Branch: fix/continuous-range-manual-backpressure
- Created directly from current main commit a27eeb04e2c633c7101330ba009f8cd0a8024eb0 (the merge revert of PR #9).
- Target remains main. User performs all merges; do not merge.

Why PR #9 failed:
- WebTorrent 1.9.7 uses streamx Readable for File.createReadStream().
- streamx v2.12.5 Readable.pipe(destination, callback) does NOT accept Node's { end: false } options object.
- On readable end, streamx's ReadableState.updateNonPrimary() calls destination.end() automatically.
- PR #9 used stream.pipe(res, { end: false }); the object was ignored as a callback, so the first 4 MiB segment ended the HTTP ServerResponse. The code then attempted to pump later segments into an already-ended response. This explains the regression; do not reuse that implementation.
- Upstream sources inspected: webtorrent/webtorrent v1.9.7 lib/file-stream.js and mafintosh/streamx v2.12.5 index.js.

Replacement in server/downloader/worker.js:
- Open-ended Range parsing now maps bytes=N- to bytes N through EOF (fileSize - 1). Explicit bounded and suffix ranges retain their existing behavior.
- Bounded WebTorrent reads remain 4 MiB each, so each FileStream selects only a small piece interval, not the whole multi-GB file.
- Removed stream.pipe() from the segmented response path. Each FileStream is consumed with data events and written directly using res.write().
- On res.write() backpressure, pause the current FileStream and resume it on res drain. If a segment finishes while the HTTP response is backpressured, do not create the next FileStream until drain.
- Wait for each FileStream close before creating the next one, ensuring its WebTorrent selection is deselected before moving on.
- The HTTP response remains open across segments and is ended only after the complete requested range has been written.
- activeStreams now stores one HTTP response session object for the lifetime of the GET, not the individual short-lived FileStreams. The session owns the current FileStream and implements destroy(), so closeAllStreams() still cancels active playback during pause/stop/cleanup.
- Rolling RAM window size, rewind cushion, priority, eviction, prebuffer and RAM watchdog were not changed.
- Added segment-level error/early-close diagnostics and response-level STREAM_CLEANUP details, including streamedBytes and segmentsCompleted.
